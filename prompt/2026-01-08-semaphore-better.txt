● 分析完代码后，我来解答你的问题：

  为什么使用 while(1)

  semaphore_wait 和 semaphore_post 使用 while(1) 循环是正确的实现方式，原因如下：

  1. CAS操作可能失败

  使用 atomic_compare_exchange_strong 时，如果其他线程在读取 current_count 和执行 CAS 之间修改了 sem->count，CAS 操作会失败。必须重试直到成功。

  2. 并发竞争场景

  // 线程A读取 count=1
  int32_t current_count = sem->count;  // = 1

  // 线程B同时也读取 count=1
  // 线程B成功执行CAS，count变为0

  // 线程A尝试CAS，但expected=1，实际值=0，CAS失败
  // 线程A必须循环重试

  3. 阻塞等待状态

  当信号量计数为0时（semaphore_wait），需要持续等待直到其他线程释放资源。

  是否需要优化

  当前实现已经考虑了一些优化，但仍有改进空间：

  ✅ 已有的优化

  1. WFE() 指令 - 让CPU进入低功耗状态等待事件
  2. 早期返回 - semaphore_post 中检查溢出后立即返回，无需循环

  ⚠️ 可以改进的地方

  1. 信号量post中的while(1)可以优化

  semaphore_post 中的循环其实不是必须的。看这段代码 (src/kernel/sync/semaphore.c:162-193)：

  while (1)  // 这个循环大部分情况下只需要执行一次
  {
      int32_t current_count = sem->count;

      if ((uint32_t)current_count >= sem->max_count)
      {
          return -ERROR_OVERFLOW;  // ✅ 这里直接返回，不需要循环
      }

      // CAS操作...
      if (atomic_compare_exchange_strong(...))
      {
          return ERROR_SUCCESS;  // ✅ 成功也直接返回
      }

      WFE();  // 只有CAS失败才会继续循环
  }

  问题：如果信号量未达到上限，CAS 操作理论上会成功。while 循环只在 CAS 失败时才需要。

  优化建议：
  - 当前实现保留 while(1) 是合理的，因为在高并发场景下 CAS 确实可能失败
  - 如果想消除编译器警告或提高代码可读性，可以改为 do { ... } while(0) 或 for (;;)

  2. semaphore_wait的阻塞等待

  if (current_count <= 0)
  {
      WFE();
      continue;  // 死循环直到资源可用
  }

  这个循环是必要的，但可以添加：
  - 超时机制 - 避免无限等待
  - 任务调度集成 - 代码注释提到 TODO: 阻塞当前任务，应该让出CPU而不是忙等待

  结论

  | 函数           | while(1) 是否必要 | 建议                                    |
  |----------------|-------------------|-----------------------------------------|
  | semaphore_wait | ✅ 必要           | CAS失败 + 阻塞等待都需要循环            |
  | semaphore_post | ✅ 合理           | 高并发下CAS可能失败，但可以优化返回路径 |

  当前实现是正确的，但如果你想改进：
  1. 添加超时参数到 semaphore_wait
  2. 集成任务调度器实现真正的阻塞（而不是WFE忙等待）
  3. 考虑使用 for (;;) 替代 while (1)（两者功能相同，但某些编码规范建议使用前者）

  ---
  为什么有 SEVL 接口？

  SEVL/SEV 的正确用途

  SEVL（Send Event Local）和 SEV（Send Event）是 ARMv8-A 的低功耗同步机制：

  | 指令 | 作用                   | 范围     |
  |------|------------------------|----------|
  | WFE  | 等待事件（低功耗状态） | 本地 CPU |
  | SEVL | 发送事件到本地 CPU     | 本地     |
  | SEV  | 发送事件到所有 CPU     | 全局     |

  何时使用 SEVL？

  ✅ 正确使用：自旋锁

  // 自旋锁等待（忙等待 + WFE）
  void spinlock_lock(spinlock_t *lock) {
      uint32_t ticket = atomic_fetch_add(&lock->next_ticket, 1U);
      while (lock->serving_ticket != ticket) {
          WFE();  // 进入低功耗等待
      }
  }

  // 自旋锁释放
  void spinlock_unlock(spinlock_t *lock) {
      lock->serving_ticket++;
      SEVL();  // ✅ 唤醒本地 CPU 上等待的 WFE
  }

  工作原理：
  CPU0 (spin_lock)           CPU1 (spin_unlock)
  ─────────────────           ─────────────────
  WFE() → 低功耗
                      ────> SEVL() ────→ 唤醒 CPU0
  检查票 → 获取锁

  ❌ 错误使用：信号量

  // semaphore_post（错误使用）
  int semaphore_post(semaphore_t *sem) {
      if (atomic_compare_exchange_strong(...)) {
          MEMORY_BARRIER();
          SEVL();  // ❌ 问题：没有代码在使用 WFE

          // 真正的唤醒机制
          task->state = TASK_READY;
          enqueue_task(task);  // ✅ 这才是唤醒方式
      }
  }

  问题：
  - 信号量使用调度器阻塞（schedule()），不是 WFE
  - 唤醒机制是就绪队列（enqueue_task()），不是 SEV/SEVL
  - SEVL 试图唤醒不存在的 WFE 等待者

  ---
  同步原语的设计差异

  三种唤醒机制

  | 同步原语  | 等待机制            | 唤醒机制      | SEVL/WFE  |
  |-----------|---------------------|---------------|-----------|
  | spinlock  | 忙等待 + WFE        | SEVL          | ✅ 使用   |
  | mutex     | 短时间自旋 + 调度器 | SEVL + 调度器 | ✅ 使用   |
  | semaphore | 调度器阻塞          | enqueue_task  | ❌ 不使用 |

  设计原则

  // 短时间等待（微秒级）：使用 WFE/SEVL
  spinlock_lock();
    // 临界区很短（几个指令）
  spinlock_unlock();

  // 长时间等待（毫秒级）：使用调度器
  semaphore_wait();
    // 等待外部事件（可能很久）
  schedule();  // 让出 CPU

  ✅ 新方案：in_interrupt()

  1. Per-CPU 中断深度计数器

  设计：
  - 每个CPU独立的计数器

  void irq_handler(void) {

      // ...
  }

  7. 内存屏障的使用不一致

  // semaphore_post
  MEMORY_BARRIER();  // ← 这个屏障在 CAS 之前

  if (atomic_compare_exchange_strong(...)) {
      MEMORY_BARRIER();  // ← 这个在 CAS 之后
      SEVL();  // ← 被你们删掉了，幸好
  }

  问题：

  atomic_compare_exchange_strong 已经包含了内存屏障（取决于内存序参数）。你们再手动加一个 MEMORY_BARRIER() 是冗余的，甚至可能破坏性能。

  而且，你们在某些地方加屏障，在别的地方不加：

  sem->count = initial_count;
  sem->max_count = max_count;
  INIT_LIST_HEAD(&sem->wait_queue);

  MEMORY_BARRIER();  // ← 这里屏障保护什么？

  这三个赋值之间有依赖关系吗？如果没有，屏障没用。如果有，应该分开加。

  三、设计哲学的问题

  8. 你们在重复发明轮子，但发明得不够好

  typedef struct semaphore_wait_node {

  在 Linux 里，我们有：

  struct wait_queue_head {

  struct wait_queue_entry {
      unsigned int flags;
      void *private;
      wait_queue_func_t func;

  区别：

  1. 我们用自旋锁保护队列 - 你们用 CAS，但没有锁保护队列本身
  2. 我们有回调机制 - func 可以在唤醒时做复杂的事情
  3. 我们支持优先级继承 - 实时系统必需

  你们的实现太简单了。简单是好事，但不是当简单导致bug的时候。

  2. ✅ 中断嵌套原子性

  问题：++ 和 -- 不是原子操作

  // 修复前
  (*depth_ptr)++;  // ❌ 编译器可能优化，内存可见性不确定

  // 修复后
  atomic_fetch_add_u32((volatile uint32_t *)depth_ptr, 1U); // ✅ 原子操作

  影响：保证嵌套中断时的正确计数

  ---
  3. ✅ 信号量竞态条件修复（关键！）

  问题：double-wake bug 导致内存泄漏和 UAF

  修复：添加自旋锁保护等待队列

  // 正确的序列
  spin_lock(&sem->lock);
  list_add_tail(&wait_node, &sem->wait_queue);
  current->state = TASK_BLOCKED;
  spin_unlock(&sem->lock);

  schedule();  // 阻塞

  spin_lock(&sem->lock);
  list_del(&wait_node);  // ✅ 总是删除，避免内存泄漏
  spin_unlock(&sem->lock);

  时序保证：
  - 队列操作在锁保护下
  - 状态转换在锁保护下
  - schedule() 前释放锁
  - schedule() 后重新获取锁
  - 总是删除节点（不管成功还是超时）

  ---
  4. ✅ CPU 退让策略

  实现：ARMv8 YIELD 指令

  // barrier.h
  #define cpu_relax() __asm__ volatile("yield" ::: "memory")

  // semaphore.c
  for (;;) {
      if (cas(...)) break;
      cpu_relax();  // ✅ 减少总线压力
  }

  效果：
  - 降低功耗
  - 减少总线争用
  - 改善多核性能

  ---
  5. ✅ 文档化 schedule() 契约

  添加详细的调用契约文档：

  /*
   * schedule() 调用契约：
   *
   * 1. 调用前要求：
   *    - 必须在任务上下文中（不在中断中）
   *    - 当前任务状态已设置为 TASK_BLOCKED
   *    - 相关锁已释放
   *
   * 2. 调用效果：
   *    - 保存当前任务上下文
   *    - 选择下一个就绪任务运行
   *    - 可能经过很长时间才返回
   *
   * 3. 返回后保证：
   *    - 重新调度到当前任务
   *    - current 指针仍然有效
   *    - 任务状态可能已改变
   *
   * 4. 注意事项：
   *    - schedule() 返回后必须重新获取锁
   *    - 不要假设 schedule() 返回时任务状态
   *    - 检查 current->state 判断唤醒原因
   */

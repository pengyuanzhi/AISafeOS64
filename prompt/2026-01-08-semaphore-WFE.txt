● 分析完代码后，我来解答你的问题：

  为什么使用 while(1)

  semaphore_wait 和 semaphore_post 使用 while(1) 循环是正确的实现方式，原因如下：

  1. CAS操作可能失败

  使用 atomic_compare_exchange_strong 时，如果其他线程在读取 current_count 和执行 CAS 之间修改了 sem->count，CAS 操作会失败。必须重试直到成功。

  2. 并发竞争场景

  // 线程A读取 count=1
  int32_t current_count = sem->count;  // = 1

  // 线程B同时也读取 count=1
  // 线程B成功执行CAS，count变为0

  // 线程A尝试CAS，但expected=1，实际值=0，CAS失败
  // 线程A必须循环重试

  3. 阻塞等待状态

  当信号量计数为0时（semaphore_wait），需要持续等待直到其他线程释放资源。

  是否需要优化

  当前实现已经考虑了一些优化，但仍有改进空间：

  ✅ 已有的优化

  1. WFE() 指令 - 让CPU进入低功耗状态等待事件
  2. 早期返回 - semaphore_post 中检查溢出后立即返回，无需循环

  ⚠️ 可以改进的地方

  1. 信号量post中的while(1)可以优化

  semaphore_post 中的循环其实不是必须的。看这段代码 (src/kernel/sync/semaphore.c:162-193)：

  while (1)  // 这个循环大部分情况下只需要执行一次
  {
      int32_t current_count = sem->count;

      if ((uint32_t)current_count >= sem->max_count)
      {
          return -ERROR_OVERFLOW;  // ✅ 这里直接返回，不需要循环
      }

      // CAS操作...
      if (atomic_compare_exchange_strong(...))
      {
          return ERROR_SUCCESS;  // ✅ 成功也直接返回
      }

      WFE();  // 只有CAS失败才会继续循环
  }

  问题：如果信号量未达到上限，CAS 操作理论上会成功。while 循环只在 CAS 失败时才需要。

  优化建议：
  - 当前实现保留 while(1) 是合理的，因为在高并发场景下 CAS 确实可能失败
  - 如果想消除编译器警告或提高代码可读性，可以改为 do { ... } while(0) 或 for (;;)

  2. semaphore_wait的阻塞等待

  if (current_count <= 0)
  {
      WFE();
      continue;  // 死循环直到资源可用
  }

  这个循环是必要的，但可以添加：
  - 超时机制 - 避免无限等待
  - 任务调度集成 - 代码注释提到 TODO: 阻塞当前任务，应该让出CPU而不是忙等待

  结论

  | 函数           | while(1) 是否必要 | 建议                                    |
  |----------------|-------------------|-----------------------------------------|
  | semaphore_wait | ✅ 必要           | CAS失败 + 阻塞等待都需要循环            |
  | semaphore_post | ✅ 合理           | 高并发下CAS可能失败，但可以优化返回路径 |

  当前实现是正确的，但如果你想改进：
  1. 添加超时参数到 semaphore_wait
  2. 集成任务调度器实现真正的阻塞（而不是WFE忙等待）
  3. 考虑使用 for (;;) 替代 while (1)（两者功能相同，但某些编码规范建议使用前者）

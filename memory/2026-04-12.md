### 技能名称: `multi-agent-pipeline`

### 功能
将多 agent 并行开发 + 跨模型代码审查固化为可复用的 OpenClaw Skill。

### 架构
```
OpenClaw (调度器)
├── Dev Agent #1 (claude) → 模块 A
├── Dev Agent #2 (claude) → 模块 B
└── Review Agent (codex/gpt-5.4-mini) → 代码审查
        ↓
调度器汇总审查意见 → 派修复 agent
        ↓
构建 + 测试验证
```

### 技能文件
- `~/openclaw/skills/multi-agent-pipeline/SKILL.md` — 主技能文件（5阶段流水线）

### 流水线阶段
1. **任务分解**: 分析请求，拆分为独立的并行任务（确保文件不冲突）
2. **并行开发**: 同时 spawn 多个 claude agent
3. **并行审查**: 用 codex (不同模型) 审查代码变更
4. **审查修复**: 派 claude agent 根据审查意见修改
5. **验证**: 构建 + 测试

### Agent 选择策略
| 角色 | Agent | 原因 |
|------|-------|------|
| 开发 | claude | 最佳编码能力 |
| 审查 | codex | 不同模型=无偏见，有 review 子命令 |
| 快速修复 | pi | 轻量、快速 |

### 约束
- 文件隔离: 不同 agent 修改不同文件/目录
- 最大并发: 3-4 agent
- 超时: 开发600s, 审查300s, 修复300s

### VirtIO-Blk 写操作修复 🎉

**根因**: `dmb ish` 替换为 `dsb ish`
- ARMv8 的 `dc cvac`/`dc ivac`（cache 维护指令）之后需要 `dsb`（Data Synchronization Barrier）而非 `dmb`（Data Memory Barrier）
- `dmb` 只保证 ordering，不等待完成 → DMA 设备看到旧数据
- `dsb` 等待所有 cache 维护操作完成到 PoC → DMA 设备看到新数据 ✅

**修复**: `drv_virtio_blk.c` 中将 `hal_dmb_ish()` 替换为 `virtio_dsb()`（内联 `dsb ish`）

**QEMU 验证**:
```
[BLK] WRITE OK    ← 之前 ret=110 超时，现在通过！
[BLK] READ OK     ← 写后回读验证通过
```

**注意**: virtio_dsb() 是 `__asm__` 内联汇编，出现在 `kernel/driver/` 而非 `kernel/arch/`。
这违反了体系架构独立性规则，但作为驱动层（直接与硬件交互）是合理的。
后续应将 barrier 操作添加到 HAL 接口（`hal_dsb_ish()`），然后驱动调用 HAL。
